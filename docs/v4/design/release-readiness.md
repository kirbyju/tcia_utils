## Workflow assessment and limits

The candidate implements dataset discovery and citation enrichment, dataset-scoped participant identity, clinical evidence with inference/conflict/source fields, public and controlled availability, and offline selection/export. It preserves original response fields, request-level release provenance, capability errors, and page boundaries. A terminal cursor page is complete for that iteration; bounded clinical, controlled, annotation, and related-analysis results remain `unknown` for exhaustive use. The source service repair is required before the hosted participant, clinical, and non-DICOM notebook workflows can be advertised as working.

Exports account for every captured row and split public `SeriesInstanceUID`, public `imageUrl`, and controlled `drs_uri` into route-specific CSVs with one recognized Data Retriever column each. Aspera package/path evidence uses a separate JSON handoff. Source images require an explicit inclusion choice. The participant `Asset` response has no public series UID or delivery location, and the public non-DICOM response has no location detail; the exporter leaves these unresolved. A public DICOM series handoff therefore requires direct `idc-index` verification from an evidenced DOI or reviewed identifier. Controlled inventory and DRS URIs are metadata, not retrieval authorization. No phase-one method downloads imaging payloads or promises full-cohort clinical export.

The code review found no further blocking defect in the T08 selection/accounting, T09 facade, or final T10 notebooks and docs. Notebook 02 verifies the visible TCIA DOI against the IDC row's source DOI, keeps IDC version, patient ID, source DOI, and license evidence in its selection companion, and writes a public-series manifest without downloading data. Notebook 04 writes a controlled DRS metadata handoff. The runner executes the built wheel and fails on fixture API errors or unsafe output. A parser-only check generated all three CSV route manifests from the synthetic T08 selection input, then loaded them through Data Retriever's actual Go spreadsheet parsers at revision `6a28e3a` using a temporary test overlay. `SeriesInstanceUID` retained `1.02.003`; the image and DRS files populated only their intended route fields. `GOPROXY=off go test -overlay=... ./core/app -run '^TestV4ManifestParseOnly$' -count=1` passed. The overlay, build cache, and generated files were outside both repositories; no transfer ran and no Data Retriever source changed. T11's final clean-install and exact CI-command checks passed locally; hosted CI remains unverified.

## Release gates and supported-server policy

1. Integrate and independently review the final five notebooks, support module, runner, guide, and T11 CI/package changes. Execute deterministic fixture notebooks using an installed wheel from outside the source checkout; record exact package and `idc-index` versions and inspect output for credentials, private paths, and unintended payload calls. Execute only bounded live metadata variants, labeling unavailable routes.
2. Run the full v4 test suite and build wheel and source archive from the final clean integration revision. Verify archive inventories, `httpx` as the only core dependency, and clean wheel and source-archive installs. Run tests against both installed artifacts outside the source tree on the declared Python floor; obtain hosted CI matrix results for Python 3.11–3.13. Record hashes and run links.
3. Retain the parser-only Data Retriever result above as local interoperability evidence for the unchanged T08 exporter. If the exporter or route columns change, regenerate and reparse all three CSVs. Keep Aspera JSON outside the CSV parser.
4. Publish/deploy the service repair under its own release process, then observe the deployed service identity and make bounded **nonempty** calls to all four repaired REST routes. Check matching MCP behavior where applicable. Re-run the client smoke against that host and record the fingerprint, installed profile, service code/version evidence, timestamps, and response statuses. A metadata fingerprint alone cannot prove service-code deployment.
5. Resolve all newly found correctness failures, update the final release notes/migration guidance, and obtain explicit publication authorization. A successful local build or fixture run is not a substitute for the hosted compatibility gate.

The supported host for this prerelease should be a configured TCIA V2 REST service with `/v2/ready` and `/v2/bundle` reporting a consistent fingerprint/profile, required capabilities available, and the four repaired routes demonstrated with nonempty bounded calls. The client reports a missing capability or HTTP failure as unavailable rather than converting it to zero data. Older hosts can support the subset of methods that pass, but they do not satisfy the full phase-one release claim.

## Release notes, migration, and rollback handoff

`4.0.0a1` is a new synchronous research-facing API centered on `TCIAClient`, not an in-place promise to preserve every 3.x provider helper. It has a Python 3.11 floor, `httpx` core dependency, optional pandas/example dependencies, explicit service configuration, typed errors, cursor-aware pages, bounded evidence results, and route-specific offline manifests. The existing 3.x `nbia`, `idc`, `wordpress`, `pathdb`, and `datacite` modules are reference source, not the v4 public interface or wheel contents. Direct `idc-index` remains the supported path for public DICOM detail. The final README and migration guide must state these changes and link the five maintained notebooks before a prerelease is tagged.

For a later authorized publication, pin both the client version and a verified service deployment in the release record. Keep the already published `3.3.5` artifact available for users who require legacy imports; if the v4 prerelease is unsuitable, install `tcia_utils==3.3.5` in a separate environment instead of assuming downgrade compatibility inside one running notebook. If a hosted service regression occurs after deployment, restore the prior service release through the service owner's rollback procedure and mark the v4 host unsupported until bounded route probes pass again. Do not silently switch the client to another host or metadata release.

After every gate above passes and the publisher explicitly authorizes it, the existing tag-triggered trusted-publishing workflow is the concrete publication route: confirm a clean reviewed commit and version, create an annotated `v4.0.0a1` tag on that exact commit, then push only that tag to the intended remote. The `publish.yml` workflow calls `validate-v4.yml` with notebooks required, builds checked artifacts, and publishes through PyPI OIDC after the protected `pypi` environment. Record the resulting workflow URL, artifact hashes, PyPI files/attestations, and the deployed-service probe separately. **No tag, push, workflow dispatch, PyPI upload, or service deployment was performed during this review.**

Conditional publication commands for the authorized release owner, from the final reviewed checkout, are:

Run the tag and push commands only after the earlier gates pass, the version/tag are confirmed unused, and the publisher authorizes that exact release commit. The push triggers the trusted-publishing workflow; inspect its validation and artifact provenance before describing the package as published.
